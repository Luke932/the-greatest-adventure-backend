18. Test di sicurezza importante

Prova a usare un guestId direttamente sulle vecchie API pubbliche:

POST http://localhost:8080/api/guests/1/companions

senza JWT.

Deve essere rifiutato, perché abbiamo deciso di non permettere più la creazione dei companion tramite semplice guestId.

Stessa cosa:

PATCH http://localhost:8080/api/guests/1/rsvp

senza JWT.

Deve essere rifiutato.

Il flusso corretto è:

TOKEN INVITO
     │
     ▼
/api/public/invites/{token}
     │
     ├── GET       → visualizza invito
     ├── PATCH     → modifica RSVP
     └── POST      → aggiunge companion

mentre:

JWT ADMIN
     │
     ▼
API PRIVATE
     │
     ├── guests
     ├── companions
     └── stats

14. Test sicurezza — niente JWT

Questo è un test che voglio assolutamente nel testbook.

Per tutti e tre:

GET    /api/public/invites/{token}
PATCH  /api/public/invites/{token}/rsvp
POST   /api/public/invites/{token}/companions

non mettere:

Authorization: Bearer ...

Devono funzionare comunque.

Questo dimostra che l'area pubblica è effettivamente pubblica.

E aggiungerei anche una nota architetturale
Le API /api/public/invites/** sono accessibili senza JWT.
L'identificazione dell'invitato avviene tramite accessToken.
Il client non invia guestId per la creazione degli accompagnatori:
il Guest viene determinato dal token dell'invito.

Questa nota ci tornerà molto utile quando svilupperemo il frontend.

A questo punto il backend ha praticamente chiuso tutto il flusso dell'invitato. Il prossimo grande blocco è il frontend: la pagina /invito/{token} che viene aperta dal pulsante presente nella mail.
